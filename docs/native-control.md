# Windows / macOS 会话控制与审批

Windows 和 macOS 默认共用 `NativeDesktopControl`，通过本机 Codex CLI 的 `app-server --listen stdio://` 创建、恢复和执行会话。两端使用相同的权限选择、网页审批和运行时生命周期；不需要单独安装 Codex SDK。

## 新会话与权限

在网页新建会话时可以选择以下权限；默认值与原 macOS client 一致。

| 选项               | 行为                                           |
| ------------------ | ---------------------------------------------- |
| 完全访问（默认）   | `danger-full-access` / `never`，无逐次命令审批 |
| 沿用本机配置       | 保留本机 Codex 的沙箱与审批配置                |
| 只读               | 只读沙箱，额外权限交给用户审批                 |
| 项目写入           | 允许修改项目，联网等额外权限交给用户审批       |
| 项目写入并允许联网 | 允许修改项目和联网，其他额外权限交给用户审批   |

权限选项只用于新会话；恢复已有会话保留其设置。受限模式将审批交给用户，不自动批准。操作系统权限及本机强制策略仍然有效。

## 网页审批范围

Monitor 自己承载的 App Server 会话支持命令执行、文件修改、额外文件系统与网络权限三类审批。文件审批展示路径与差异；差异未就绪时不能批准。“允许本次”只批准当前操作，额外权限仅本轮有效。

审批使用原始 App Server 请求 ID 和原进程回调答复。同名请求 ID 在不同会话中分别处理；断线、轮次结束或请求已被解决时取消等待，旧审批不能在替代进程上重放。网页读取与答复继续验证管理员、登录设备、工作空间和会话范围。

由 Codex 桌面持有的会话通过 owner IPC 转发消息、停止与压缩，审批仍在桌面处理。结构化提问与 MCP elicitation 尚无网页答复入口。

文本输入显式携带 `text_elements: []`，新建、恢复及桌面 owner 转发使用同一格式。桌面 owner 会保留原始输入用于渲染，不能依赖 CLI 补齐默认值；缺少该字段会使部分桌面版本在读取 `text_elements.length` 时触发会话页面错误。

## CLI 与旧通道

### 按消息选择桌面通道

默认仍通过统一 App Server 控制器创建或续接会话。追加表单可勾选“桌面通道”；消息请求使用可选的 `channel: "desktop"`，未勾选时省略该字段，兼容旧 client。

新建表单使用默认通道，并保留模型、思考级别和权限选择；旧新建草稿中的桌面通道标记会被清理，输入内容、附件、目标和已有请求回执继续保留。桌面工具创建会话不能保证继承界面选中的完全访问，因此新建页不提供此选项。

追加勾选后使用桌面 `send_message_to_thread`；不使用原来的裸 owner `thread-follower-start-turn` 作为所选桌面通道。桌面持有并正在执行的会话直接提交追加消息，沿用当前模型与 thinking，空闲时可传入下一轮的模型与 thinking 覆盖。内部状态的可选 `owner` 字段区分 monitor 运行时与桌面 owner；旧桌面 tools 桥接未报告 owner 时也保留执行中追加。消息队列持久化通道，并将它纳入请求 ID 指纹。仅 monitor CLI 正在执行、其持续目标尚未结束、运行中的会话暂时无法连接 owner 或上下文压缩期间等待；CLI 空闲后先等其进程退出再交接同一个会话，active goal 不被自动暂停或中断。发送前仍由控制器检查 CLI 运行时，状态检查后发生的交接冲突也会保留在队列中。桌面连接或发送失败直接报告，回执不确定时不重发。

追加表单的通道选择与草稿按工作空间隔离；排队时锁定，刷新后恢复，成功发送后重置。更新 Server 和对应 client 才能使用此能力；旧 client 未上报支持时不提供可选入口。

`MONITOR_CODEX_CLI` / `--codex-cli` 可指定 Codex CLI；也支持桌面运行环境的 `CODEX_APP_RUNTIME_CLI_PATH`。Windows 优先检查指定桌面程序旁的 `resources/codex.exe`，再通过 `Get-AppxPackage` 获取当前用户的 Store 安装位置，并检查常见独立安装目录和可读取的 Windows Store 安装目录，最后才使用已有 `OpenAI/Codex/bin` 运行时缓存。此顺序避免 `WindowsApps` 拒绝目录枚举时漏掉桌面安装，以及桌面升级后继续选中旧缓存。找不到时明确提示配置 CLI 路径，不会将桌面 GUI 当作 CLI 启动。

macOS 沿用桌面 `.app` 内 CLI 自动发现。两端都沿用当前用户的 Codex 配置与登录，`CODEX_HOME` 控制读取及执行的数据目录。

显式设置 `MONITOR_CODEX_PIPE` / `--codex-pipe` 会使用旧的桌面 tools 通道，保留原行为，不提供新的权限选择与网页审批。要使用统一通道，应移除此显式设置并重启 client。其他操作系统继续保留原桌面桥接行为。

更新后重新构建并重启 Server 和对应 client，网页权限控件和 client 审批回调需同时更新。后台启动器会按已有进程身份核验规则加载新构建；本次代码修改不直接重启正在运行的服务。

## 验证边界

自动测试覆盖 Windows/macOS 默认控制器选择、显式旧 pipe、Windows CLI 安装路径发现、真实 JSON-RPC 帧的审批等待与答复、文件差异、跨会话隔离、断线取消，以及原桌面 owner 的转发和不确定回执处理。Windows 路径查找使用临时目录中的模拟安装，不运行其中的可执行文件。

2026-11-16 在 macOS 完成构建、201 项后端测试（普通 Node 26.12.1；1 项 Windows 专用检查跳过），以及桌面和手机端 10 项审批、12 项新建与目标浏览器测试。审批和旧 client 兼容测试分别使用各自的独立 fixture 服务。

运行环境记录：Node 24.13.0 的全量测试在上传用例结束后报告 `EPIPE`；应用内置 Node 24.22.1 的 PTY 等原生依赖测试失败。普通 Node 26.12.1 下全量测试通过，与既有 macOS client 的验证环境一致。

2026-11-16 Windows 本机补充验证：从桌面异常堆栈定位到其实际文本渲染函数，复现缺失 `text_elements` 的输入会抛出 `Cannot read properties of undefined (reading 'length')`；新建、恢复与 owner 转发的修复后输入均通过该函数。36 项相关自动测试及构建通过。实机 `WindowsApps` 枚举返回 `EPERM`，通过安装信息已正确发现桌面自带的 `0.169.0-alpha.11.1`，不再选中 `0.167.0-alpha.4.1` 缓存。

此验证未向真实会话发送测试消息，也未重启承载诊断会话的 client。已有会话的桌面页面恢复、Windows 系统沙箱及真实审批仍需在加载新构建后确认；模拟服务测试和独立渲染函数验证不等同于桌面端到端验收。
